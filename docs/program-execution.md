# تنفيذ البرامج المعتمدة واختيار مزودي الخدمة

## طريقة العمل

1. بعد اعتماد تمويل بطاقة حاجة السوق بالكامل، تظهر في «البرامج المعتمدة وفقًا للتخصص». التحقق يعتمد على مجموع المساهمات المعتمدة الفعلي، وليس النسبة المقربة أو اسم الحالة وحده.
2. افتح تفاصيل البطاقة بالنقر على الصف، أو اضغط «مزود الخدمة». بيانات الحاجة والتكلفة والتمويل معروضة للقراءة فقط.
3. تظهر جهات التدريب المطابقة للبرنامج والتخصص في منطقة مستهدفة واحدة على الأقل. يوضح النظام هل تغطي الجهة جميع المناطق أم جزءًا منها.
4. إذا كان البرنامج «تشغيليًا»، تظهر قائمة مستقلة لجهات التوظيف. يلزم أن يجمع العرض النشط القطاع والتخصص وشكل رعاية عليه «هل الرعاية توظيف؟ نعم» في العرض نفسه. جميع حالات قدرة/رغبة/رعاية مسموحة؛ لا يوجد حد أدنى للقدرة المالية.
5. يمكنك البحث والتنقل بين الصفحات واختيار أكثر من جهة. الاختيارات تبقى مسودة في جلسة المتصفح حتى مراجعة الحفظ وتأكيده. البحث وحده لا ينشئ أي سجل تنفيذ.
6. احفظ كحالة «جديد» إذا لم تكتمل الاختيارات. لبدء التنفيذ أو إكماله، اختر مزود تدريب واحدًا على الأقل؛ والتشغيلي يحتاج جهة توظيف أيضًا.
7. تغيير الحالة إلى «مكتمل التنفيذ» يعرض تحذيرًا واضحًا. بعد التأكيد، يمنع الخادم كل تعديل لاحق في بيانات التنفيذ والجهات المرتبطة، حتى لمدير النظام الأعلى.
8. كل حفظ يسجل المستخدم والوقت والحالة والاختيارات والملاحظات قبل التعديل وبعده. لا تتغير مساهمات التمويل أو حالات تطور الجهات نتيجة اختيار المزودين.

## قرارات مؤكدة وحدود النطاق

المصدر: المستند المرفق، النسخة 3.0 بتاريخ 05/10/2026، ويحمل وصف «مسودة»، والصورتان المرفقتان. حالات التنفيذ وقفل الاكتمال مأخوذة من ملاحظات الصور والطلب، وليست فصلًا مستقلًا ندّعي وجوده في المستند.

| القرار | التطبيق |
|---|---|
| جغرافيا جهات التوظيف | وافق المستخدم على عدم تطبيق فلتر مناطق؛ لا توجد علاقة موثوقة حاليًا. يظهر توضيح بذلك. لم تُضف مناطق إلى الشراكات. |
| مناطق مزود التدريب | وافق المستخدم على الاكتفاء بمنطقة مشتركة واحدة، مع بيان التغطية الجزئية/الكاملة. «عالمي» لا يعني تغطية كل المناطق. |
| الاختيارات الإلزامية | وافق المستخدم على مزود تدريب للتدريبي، ومزود تدريب وجهة توظيف للتشغيلي، عند البدء أو الإكمال. |
| عدد سجلات التنفيذ | إعداد واحد لكل بطاقة، يرتبط بعدة مزودين وجهات توظيف. يمنع القيد الفريد التكرار. |
| معنى تعديل | تعديل التنفيذ فقط. لا يعيد فتح الأساس المالي أو معايير بطاقة ممولة. |
| السجلات القديمة للمزودين | تضاف علاقة البرنامج بقيمة فارغة، دون تخمين. تبقى البيانات القديمة محفوظة، وتظهر رسالة استكمال؛ تستبعد من المطابقة حتى تحديد البرنامج. |
| تاريخ البرنامج | بيانات البرنامج في بطاقة الحاجة تظل نسختها المحفوظة. تغيير نوع البرنامج المرجعي لاحقًا يمنع بدء/إكمال التنفيذ حتى مراجعة المسؤول. |
| التشغيل والعلاقات | مزود التدريب يطابق البرنامج مباشرة. جهة التوظيف تطابق القطاع والتخصص وعرض التوظيف؛ لا نخترع لها علاقة برنامج جديدة. |

لم نغير الهيكل الحالي «المزود ← المناطق ← التخصصات»، أو آلية مطابقة الرعاة المالية، أو تحويل الشراكات إلى رغبة، أو سياسات حذف السجلات الأخرى. هذه حزمة الصفحتين ومتطلب ارتباط المزود بالبرنامج؛ ليست إعادة تنفيذ جميع وحدات BRD.

## الصلاحيات

- «البرامج المعتمدة وفقًا للتخصص»: عرض، تصدير Excel، تصدير PDF.
- «اختيار مزودي تنفيذ البرامج»: عرض، إضافة إعداد، تعديل إعداد، تغيير حالة، تصدير Excel، تصدير PDF.
- العرض لا يمنح الحفظ. التعديل لا يمنح تغيير الحالة. منع المستخدم الفردي يبقى مقدمًا حسب النظام الحالي.
- الترحيل لا يغير أي دور أو منحة حالية. يمنح مدير النظام الصلاحيات المناسبة من محرر الأدوار الحالي.
- المسارات: `/execution/`، `/execution/assignments/`، `/execution/<id>/providers/`.
- الرابطان خارج الإدارة ولا يفتحانها تلقائيًا. رابط الاختيار العام يفتح قائمة بطاقات مخولة بدل رابط ناقص رقم البطاقة.

## الترحيلات

1. `service_providers.0004_serviceprovider_program`: عمود برنامج اختياري للسابق، مع `PROTECT`.
2. `market_needs.0003_needexecution_executionprovider_executionemployer_and_more`: إعداد التنفيذ وروابط الجهات، قيود فريدة وحالات/تاريخ اكتمال وفهرس.
3. `access_control.0004_execution_modules`: تسجيل الصفحتين وصلاحياتهما دون منحها للأدوار.

كلها إضافية؛ لا حذف أو إعادة تسمية لعلاقات موجودة، ولا تحويل بيانات تغطية. لا توجد مرفقات جديدة لهذه المرحلة؛ تبقى مرفقات التمويل الخاصة كما هي.

## نتائج التحقق المحلي

- `manage.py check`: بلا ملاحظات. `makemigrations --check --dry-run`: لا تغييرات مفقودة. `git diff --check`: ناجح.
- اختبارات `market_needs service_providers access_control core`: **198 اختبارًا، ناجحة، مع تخطي 7 اختبارات تتطلب أقفال قاعدة بيانات حقيقية**.
- اختبارات المثبت المستقلة: **7 اختبارات ناجحة**: النسخ الاحتياطي، التكرار، الدمج المستقل، التعارض، حماية الروابط، فشل الكتابة، ومنع استعادة تمحو تعديلًا أحدث.
- Chromium 153: تأكيد الحفظ، اختيار عبر صفحات، بدء التنفيذ وإكماله وقفل التعديل، نافذة تفاصيل، القوائم، الجوال، Excel لجميع النتائج، PDF فعلي؛ بلا أخطاء JavaScript.
- تشغيل جميع اختبارات المشروع قبل آخر تحسينات العرض: 483 اختبارًا، 10 إخفاقات وخطأ واحد في `accounts`، و7 متخطاة. أُعيدت اختبارات الحسابات على نسخة Git الأصلية فظهرت **نفس الأسماء الـ11 ونفس الأسباب**. تتعلق بتوقعات قديمة لتوجيه الدخول/CSRF وتحديد المحاولات وعدد الاستعلامات؛ ليست معالجة في هذه الحزمة. انظر `VERIFICATION.md`.
- **Docker/MySQL غير متاحين محليًا؛ لم ندّع نجاح الاختبارات المتزامنة على MySQL.** ملف `compose.execution-tests.yaml` يشغّل MySQL 8.4 مؤقتًا في شبكة منفصلة وذاكرة مؤقتة دون ربط مجلدات الإنتاج. ينفذه `deploy.sh` قبل ترحيل الإنتاج ويتوقف إذا فشل.
- لم يتم نشر هذه الحزمة أو دفع التغييرات إلى GitHub من هذه الجلسة.

## التشغيل بعد التثبيت

امنح الصلاحيات، ثم استكمل البرنامج التدريبي للمزودين الحاليين، وتأكد من تفعيل «هل الرعاية توظيف؟» للأشكال الصحيحة في الكتالوج الحالي. افتح بطاقة ممولة، اختر الجهات، راجع التأكيد، ثم جرّب دورة جديد ← تحت التنفيذ ← مكتمل التنفيذ. لا تستخدم بطاقة حقيقية لتجربة الاكتمال إن كنت ستحتاج تعديلها لاحقًا؛ لا توجد إعادة فتح في هذا النطاق.
